## Part 3 — Mobile gallery: autoplay, loop, debounce + a console warning fix

On `ProductDetail.tsx`'s mobile image carousel (already a swipeable `embla-carousel-react`
carousel from the original launch-day work):

- **Circular looping**: `opts={{ loop: true }}` — swiping back from the first image wraps to the
  last, and vice versa. Verified directly against the live embla API (`scrollPrev()` from index 0
  → wraps to the last index; `scrollNext()` from the last → wraps to 0).
- **Auto-advance every 2.5s** via the `embla-carousel-autoplay` plugin (newly added dependency),
  configured `Autoplay({ delay: 2500, stopOnInteraction: false })`, held in a `useRef` so the
  plugin instance is stable across re-renders.
- **Debounce on interaction**: `stopOnInteraction: false` doesn't just keep autoplay running after
  a swipe — it makes the plugin **reset its timer** on interaction rather than continuing the
  interrupted countdown. Verified directly: paused mid-countdown at 1149ms remaining, a simulated
  swipe start/end cycle resulted in a fresh ~2353ms countdown afterward, not a continuation.
  (**Testing note**: this had to be verified by reaching into the live embla API via a temporary
  `window.__debugCarouselApi` hook — removed after — because this remote browser tooling's
  synthetic drag/touch events don't reliably trigger embla's real gesture recognition, and
  `document.hidden` is `true` in that environment which pauses autoplay via the Page Visibility
  API. Neither is a real-world concern; both are testing-environment artifacts.)
- **Fixed a React 18 console warning**: `fetchPriority` (camelCase) as a JSX prop on `<img>`
  doesn't work in React 18's runtime (only the type declarations know about it, matching a future
  React version) — it warned and never reached the DOM. Fixed in `ProductDetail.tsx`'s mobile and
  desktop galleries using the same imperative-ref pattern already established in `SiteMedia.tsx`:
  `ref={(el) => el?.setAttribute('fetchpriority', ...)}` instead of the JSX prop. (A third instance
  of this same fix, on `Collections.tsx`'s hero image, was made and then moot — that whole page was
  deleted in Part 4.)

## Part 4 — SEO: three back-to-back, partially-contradictory rounds

**Round 1 (misdiagnosed as the fix, later reverted):** client reported `/collections` and
`/size-guide` weren't showing up on Google, asked to "remove the indexing code." Initially
interpreted as: these pages were being deliberately hidden from search via a `useNoIndex()` hook
and should be made indexable instead. Did that: removed `useNoIndex()` from `Collections.tsx` and
`SizeGuide.tsx`, added real `useSeo()` calls (title/description/canonical) to both, added them to
`sitemap.xml`, added them to the bot-prerender middleware matcher with real `prerender.ts` cases.

**Round 2 (the actual intent, correcting Round 1):** client clarified — they didn't want those
pages made indexable, they wanted them **taken down entirely**, and were fine with deleting the
page code outright. This fully reversed Round 1:
- **Deleted**: `src/pages/About.tsx`, `src/pages/Collections.tsx`, `src/pages/SizeGuide.tsx`,
  `src/hooks/use-no-index.ts` (now fully unused), and their orphaned hero image assets
  (`about-hero.jpg`, `collections-hero.jpg`, `sizeguide-hero.jpg`, `collection-winter.jpg`).
- Removed their routes from `App.tsx`. Unmatched paths fall through to `<NotFound />` (404 page).
- Reverted the `sitemap.xml` / middleware matcher / `prerender.ts` entries added in Round 1 for
  those two routes.
- Fixed leftover `/collections` links in `Cart.tsx` and `Checkout.tsx` to point at `/` instead.
- **`NotFound.tsx` now sets `<meta name="robots" content="noindex, nofollow">` itself.** This
  matters because of how the SPA is served: `vercel.json` rewrites *every* unmatched path to
  `index.html` with an HTTP 200 (not a real 404 status) — client-side routing then renders
  `<NotFound />`. Without an explicit noindex signal, a JS-rendering crawler could still index this
  as thin/duplicate "page not found" content instead of correctly treating it as gone. Verified
  live: `rarstudio.co/collections` returns 200 + "404 Oops! Page not found" + `noindex, nofollow`.
- **Per-product size charts (`SizeGuideDialog.tsx`, the modal from Part 1 #1) are untouched** —
  that's a separate feature from the deleted standalone `/size-guide` page and was explicitly kept.

**Round 3 (diagnosis + name-collision reality check):** investigated why `rarstudio.co` wasn't
ranking even a week after sitemap submission:
- Confirmed `index.html`'s title/meta were already correct ("RAR Studio," not stale) — the
  "Amore" branding showing up in Google's search snippet is a **stale cached crawl** from before
  the rebrand, not a current bug. Recrawling fixes it; it doesn't self-heal instantly.
- Confirmed via Search Console's URL Inspection tool that Googlebot hit a real **5xx server error**
  crawling a product page on Aug 10 — re-tested that exact URL live with `curl` spoofing a
  Googlebot user-agent and got a clean 200 with correct title/description/JSON-LD, confirming
  whatever caused that failure isn't happening on the current code (root cause not identified —
  likely transient or since-fixed by other work).
- Walked the client through Search Console's **URL Inspection → Request Indexing** for the
  homepage, `/contact`, and a couple of product pages — explicitly framed as a **one-time bootstrap
  for a new domain**, not a recurring workflow (client correctly pushed back on doing this
  per-product routinely — confirmed that's right: the sitemap is dynamically generated from
  Supabase on every request, already includes new/removed products automatically, and Google
  already re-reads it on its own schedule (confirmed: "Last read: Aug 18" without anyone asking).
  New products need zero manual indexing action.
- **Named the actual hard problem**: "RAR Studio" is not a unique brand name. There's an
  established Lisbon architecture firm (`rar-studio.com`) and a separate Indian apparel label also
  using "RAR Studio" on Instagram (25.9K followers) — both already outrank this brand-new domain
  for the bare term "rarstudio." Explicitly did **not** promise #1 rankings; gave a realistic,
  months-not-days timeline and a concrete action list (Google Business Profile, verified Instagram
  bio link, other social profiles, real backlinks, long-tail phrases like "RAR Studio Pakistan"
  instead of fighting the contested bare name head-on).
- **One concrete code change for disambiguation**: `buildOrganizationJsonLd()` in
  [`src/lib/seo.ts`](../src/lib/seo.ts) now emits `"@type": "ClothingStore"` (a schema.org
  LocalBusiness subtype) instead of the generic `"Organization"`, with a real `PostalAddress`
  parsed from the contact info's free-text `location` field (`"Rawalpindi, Pakistan."` →
  `addressLocality: "Rawalpindi", addressCountry: "Pakistan"`). Verified live in the rendered
  JSON-LD. This is a real signal that this is a physical Pakistani clothing store, distinct from
  the other two "RAR Studio"s — everything else on the disambiguation list (Google Business
  Profile, backlinks, socials) is manual work only the client can do.
- **Explicitly declined** to build anything that pings Google's sitemap endpoint (deprecated
  years ago) or uses Google's Indexing API for general pages (officially restricted to
  JobPosting/BroadcastEvent types only — using it for an e-commerce site risks the client's domain
  trust for no reliable benefit).
